# Evals: does the desk work? (Case 04 question 1, built the L7 way)

Order followed, as the lecture asks:
1. **Kill criteria first:** [`KILL_CRITERIA.md`](KILL_CRITERIA.md). One sentence each; any one firing once means no hand-over to Riya.
2. **Every place the desk judges something.** The test-case table, [`cases.json`](cases.json), is generated by [`build_cases.py`](build_cases.py). Each row has a fixed input, expected behaviour, assertion(s) and a severity, plus the partition it covers and the kill criterion it guards. Rows were drafted with AI and reviewed by a human.
3. **Harness:** [`harness.py`](harness.py). Feed input → run → check → log → report. It talks to the desk **only over HTTP** (`/api/eval/<decision>`, password-gated, writes nothing real).
4. **Proof the harness checks something:**
   - `--break` sabotages every captured output, and the harness must catch it.
   - A **canary** row is deliberately wrong and must fail on every run.
5. **Run it twice.** Every case runs twice by default. Any verdict that flips is listed, and a flip on a critical case fires K13.
6. **Soft assertions use an LLM judge** from a different model family when `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` is set. Otherwise Gemini is used, and the report names that limitation on every run.
   - Each run writes a **blind 10% audit sample** (`audit/sample-*.csv`) with the judge's verdict hidden.
   - Fill in your verdicts, then run `--audit-compare`. Disagreements are logged to `audit/disagreements.jsonl`.
7. **Adversarial rows** sit in the same table: instructions hidden in a form, a deck, a web page, a portfolio check and a founder reply.

| Decision | Kind | Cases |
|---|---|---|
| Quote tracing (is the evidence really in the document?) | hard | Q1–Q5 |
| Fact extraction (mismatches, relabelling, injection) | hard on model output | E1–E4 |
| Portfolio conflict (direct vs adjacent) | hard on model output | C1–C9 |
| Research identity / sufficiency (namesakes, stale, contradicted) | hard on model output | R1–R8 |
| Research loop cap | hard | B1–B4 |
| Scoring rules after the model (thresholds, boundaries, units, tracing) | hard | F1–F22 |
| Feedback retrieve / conflicting corrections | hard on model output | FB1–FB6 |
| What counts as a correction | hard | CP1–CP5 |
| Founder reply classification | hard on model output | CL1–CL10 |
| Booking agent edges and tool failures (fake world) | hard | BK1–BK20 |
| Full scoring end to end | hard + soft (judge) | S1–S6 |
| Nobody auto-decided (live queue) | hard | K6a |

```
python app.py                                   # the desk, on :5057
python evals/build_cases.py                     # regenerate cases.json after editing the table
python evals/harness.py                         # all cases, twice -> evals/reports/latest.md
python evals/harness.py --only C1,BK3 --runs 1  # a subset
python evals/harness.py --break                 # prove the harness catches broken output
```

Scale, honestly: L7 puts a full suite at 150–350 cases. This one has 101, covering every decision point, its boundaries and its adversarial rows. Coverage of the known conditions is measurable; coverage of reality is not.
