PART 1
What a Test 
Case Actually Is
Not "does it seem fine." But, Binary.
Like a Driving Test, Not a Vibe Check
A driving examiner doesn't ask "did that feel like good driving?" They give a fixed route (parallel park on this street, stop at this 
junction), a specific standard (wheels within 18 inches of the curb, full stop for 3 seconds), and a checklist with boxes that get 
ticked or not. At the end: pass or fail. Not "pretty good." Not "mostly fine."
1
ROUTE GIVEN
Parallel park between the two 
cones on Elm Street
2
STANDARD
Vehicle fully inside bay, no cone 
touched, completed in one attempt
3
RESULT
☐  PASS   ☐  FAIL
A test case is this same checklist, for your agent instead of a driver.
Three Parts. All Three Required.
Just like a driving test, an effective test case for your agent isn't about subjective feeling. It comprises three non-negotiable 
components, each critical for objective evaluation:
1. A Fixed Scenario
What is the exact input the agent 
will receive? This includes the user 
prompt, system context, and any 
relevant data. No variations, no 
assumptions.
2. A Stated Standard
What does a "correct" response 
look like? This is a precise definition 
of the expected output, covering 
content, format, and behavior.
3. A Binary Checklist
A clear, unambiguous pass or fail 
judgment. Did the agent meet the 
standard for the given scenario? 
There's no "almost" in a real test.
Every single test case you write for your agent must incorporate these three elements to provide truly objective, actionable 
results.

Some Things Can Be Checked 
by a Machine. Some Can't.
Two real assertions, side by side — not descriptions of the categories, the actual checks:
HARD ASSERTION ✅ (code can run this)
if "30-day" in response and "refund_policy.pdf" in 
citations:
    return PASS
A regex or a line of code either finds it or doesn't. No one needs 
to read the output.
SOFT ASSERTION ⚠ (a person 
— or a judge — has to read it)
The agent cited the right document and the right number. 
But does the tone sound dismissive to a frustrated 
customer?
No regex catches tone. This is why Part 2 exists.
Most teams write hard assertions and skip soft ones, because soft ones are harder to write. Those are usually the ones that 
fail in ways that make it to social media.
Not a Pass Rate. A Hard Stop.
A 92% pass rate sounds good. It means 8 out of 100 
test cases fail. Depending on which 8, this is either 
fine - or a crisis.
Kill criteria are different. A condition so severe that 
if it fires even once, the system does not ship. Not 
"we'll monitor post-launch." Not "that's an edge 
case." Stop.
Write the kill criteria before you write the 
test cases. They tell you what the test 
cases need to catch.
KILL CRITERION
The agent cites refund_policy.pdf 
for a refund question.
If this ever fails, even once, the system does not ship. Not "we'll 
monitor it." Stop.
One sentence. Not a percentage. That's a kill criterion.

You Can Measure Coverage. Not Completeness.
Coverage of Your Checklist
You can achieve 100% coverage of your known 
conditions. Every documented policy and scenario can 
be systematically tested and validated.
Coverage of Reality
There will always be unforeseen edge cases, new 
attack vectors, and evolving user behaviour. This is an 
unquantifiable, ongoing challenge.
One of these is a number. The other isn't - and no formula closes that gap.

FROM METHOD TO PROMPT — DECISION 1 AS THE WORKED EXAMPLE
Write the Prompt That Writes the Table
ROLE
You are a QA test designer. You write exhaustive equivalence-partitioned test cases for an AI agent's decision logic. You do not summarize or sample — you enumerate every partition.
DECISION TO TEST
Shortlist filter: a lead-qualification agent decides whether a company should be shortlisted, based on 4 conditions:
1. Funding stage — must be Series A, B, or C
2. Company size — target band is 50–200 employees, but this is a SOFT preference, not a hard cutoff. Sizes moderately outside the band (e.g. 40s or 200s–300s) should still often be accepted; only sizes far 
outside the band should be rejected. There is no fixed number — this requires judgment.
3. B2B SaaS — yes/no
4. Certifications already procured — yes/no (if yes, this disqualifies the lead — we have nothing to sell them)
TASK
1. For each of the 4 conditions, list every equivalence partition (e.g. for Funding Stage: "within A–C", "outside A–C", "missing/unknown").
2. For the Size condition specifically, since it is soft, identify: the clearly-in-band partition, the "moderately outside, still acceptable" partition, the "far outside, not acceptable" partition, and the exact boundary 
between the second and third.
3. Identify any conditions that INTERACT — where the correct decision for one condition depends on the value of another (e.g., does a borderline size get accepted more easily if the other 3 conditions are 
strong?). If you don't have enough information to know whether an interaction rule exists, say so explicitly rather than inventing one.
4. Generate one test case per partition, plus interaction cases if found. Do not generate only a representative sample — generate the full set.
OUTPUT FORMAT
A table with exactly these columns: Input | Expected Behaviour | Assertion | Severity (Low / High / Critical)
- Severity = Low for clearly-correct, uncontested cases
- Severity = High for boundary or missing-data cases
- Severity = Critical for cases where getting it wrong would silently admit a disqualified lead or silently reject a good one with no flag for human review
CONSTRAINT
Do not stop at 4-6 rows for the sake of brevity. If the true partition count is 12 or 20, produce all of them. Flag with a note at the end: total partition count, and whether any partitions required judgment calls on 
your part due to ambiguity in this brief.

The Test That Should Fail

Most of What Your Agent Produces 
Cannot Be Hard-Asserted.
Hard Assertions
"Did this response cite the document?" - yes or no.
"Did the system refuse an out-of-scope request?" - yes or 
no.
Judgment Required
"Is this email appropriate for a board-level reader?"
"Did the agent stay within the retrieved context?" - these 
require a judge.
A test suite that only covers hard assertions misses the entire second class of failure. And the second class is usually where 
the interesting failures hide. You need a judge that can exercise judgment - reliably, automatically, on every test case, every 
run.

THE PROBLEM - AND THE FIX
A Judge From the Same Family as the Agent Shares Its Blind Spots.
Same model as agent and judge → same blind spots, invisibly. Name the limitation. Don't let it hide.
Different Model Family
Judge ≠ agent's model.
Human Audit Sample

PART 3
Adversarial Inputs
A hostile input is just a test case with intent.
An Adversarial Test Runs 
Exactly Like Any Other Test.
Same runner. Same judge. Same pass/fail log.
The only differences: the input is designed to make the 
system fail, and the expected behaviour is the system 
resisting correctly.
This is not a special category of testing requiring a different 
tool or a different team. It is three more rows in your test 
case spreadsheet - written by someone thinking like an 
attacker.
Red-Teaming =
Adversarial evaluation. A kill criterion that fires on an 
injection attempt is exactly the McDonald's lesson: the 
failure mode was predictable, the test wasn't written, 
the cost was paid anyway.
